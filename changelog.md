## 2026-10-15 — Реальный прогон на MiMo: кратность занятия, покрытие РО и порядок сложности

### Проблема
Реальный прогон (OpenRouter, `xiaomi/mimo-v2.6-flash`, без reasoning) падал на трёх шагах:
1. S08: LLM ставила кратность занятия 4 ч и 8 ч при 14 ч содержания → `HoursInfeasible` (после делителя 7 ч тем оказалось больше занятий).
2. S07: модель не привязывала часть РО (LO2.1–2.3) ни к одной теме → ошибка V-COV-01 только на утверждении каркаса.
3. S07: сложность тем убывала по программе → V-SEQ-01.

### Фикс
- `karkas/agent/skills/S01_parse_brief/run.py`, `prompt.jinja`, `schema.json`: LLM больше не выводит кратность занятия из брифа. Поле убрано из промпта и схемы (экономия токенов), а слияние ограничений в `pipeline.py` не перезаписывает `unit_hours`, заданный методистом через API/UI.
- `karkas/agent/skills/S07_module_structure/run.py`: если часть РО из S06 не раскрыта темами — одна целевая перепопытка (`missing_outcomes`, `previous_json` в промпте). Берётся вариант, раскрывающий больше РО; если и он не покрыл все — запись в `gaps`.
- `S07` `_enforce_sequence`: сложность темы, стоящей после более сложной, поднимается до предыдущей (детерминированно, без вызова LLM); каждая поправка — в `gaps`.
- Подмена кратности (`_effective_unit`) удалена: явная кратность, не делящая содержание, даёт понятную ошибку солвера, а не тихую подмену. Иначе сохранённая и применённая кратность расходились, и валидатор V-HRS-08 падал на утверждении.
- `karkas/settings.py` + `karkas/agent/llm_gateway.py`: опции `LLM_EXTRA_BODY_JSON` (например, отключение reasoning; валидатор требует JSON-объект) и `LLM_MAX_OUTPUT_TOKENS` (по умолчанию выключены). Ключ кэша учитывает их, когда заданы, иначе кэш отдал бы ответ прежнего режима. Без опций ключи прежние.
- Фикстура интеграционного теста: убрана `unit_hours` из фейкового ответа S01 (поле больше не выводится).
- Стаб сквозного теста S07 (`tests/unit/test_skills_catalog.py`) теперь покрывает LO1.1–LO1.3 одной темой.

### Проверка
- `tests/unit`: 528 passed. Новые тесты: `tests/unit/test_s07_coverage_repair.py` (ремонт покрытия, gaps, V-SEQ-01), `tests/unit/test_gateway_options_and_unit.py`.
- Полный набор с PostgreSQL до последних правок S07: 565 passed.
- Реальный прогон до S14 без ошибок V-COV и V-SEQ; дальнейший прогон блокирован окружением (см. отчёт).

## 2026-10-14 — Харденинг по итогам независимой проверки: IDOR, залипание статусов, ETag, SSRF, restore, SSE

### Проблема
Независимый проверяющий (чистый контекст, собственные негативные сценарии) нашёл 8 дефектов уровня Showstopper: IDOR по файлам и автопрогонам, навсегда залипающие статусы `*_generating` после провала/повтора задачи, сломанный If-Match/ETag, SSRF через редирект при скачивании вложений по URL, restore версии без фактического восстановления, SSE без авторизации для EventSource и без межпроцессной доставки, а также перекрытие `kit_generating`-обновлений триггером БД.

### Фикс
- **IDOR закрыт**: файл обязан принадлежать организации при привязке к программе (404 иначе); продолжение чужого автопрогона — 403 (в ответе и в `GET /agent/runs`).
- **Залипание статусов**: задачи `framework`/`kit` кладут в payload `prev_status`; при окончательном провале воркер откатывает программу из `*_generating`; ключ идемпотентности привязан к `lock_version` — повторная генерация после завершения/сбоя создаёт новую задачу, двойной клик по-прежнему дедуплицируется; `restore` запрещён во время генерации.
- **Идемпотентность HTTP**: `Idempotency-Key` на `POST /programs` возвращает ту же программу и задачу в течение 24 ч (`find_by_idempotency`); `auto_approve` доступен только сервисным ключам.
- **If-Match/ETag**: парсер сравнивает `lock_version` из ETag вида `"v<version>-<lock_version>"`; для пользовательских PATCH/approve заголовок обязателен (412 без него).
- **SSRF**: скачивание вложений по URL — ручная обработка редиректов с повторной проверкой каждого хоста по `EGRESS_ALLOWLIST` (≤ 3 хопа, userinfo отбрасывается).
- **Триггер `program_gate`**: `kit_generating` проверяется как ПЕРЕХОД — сохранение снимка версии воркером в этом статусе больше не падает с `GATE_NOT_PASSED` (иначе комплект физически не мог собраться через API+воркер).
- **SSE**: токен допускается query-параметром (EventSource не умеет заголовки), `last_event_id` — и заголовком, и query; шина получила межпроцессный мост PostgreSQL LISTEN/NOTIFY (`karkas_events`) с деградацией до in-process; очередь подписчика ограничена (drop-oldest), при подключении отправляется `: connected`.
- **Прочее**: `:adapt` и cursor пагинации валидируются (400 вместо 500), лимитер применён ко всем аутентифицированным роутерам и `/auth/login` (по IP), структурированное логирование structlog (api/worker/pipeline), `var/` в .gitignore.
