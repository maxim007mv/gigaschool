# 1. Назначение и границы документа

Документ описывает архитектуру сервиса **КАРКАС** — ИИ-агента, который по запросу методиста АЦР проектирует образовательную программу по ИТ-направлению любого объёма и формирует полный комплект материалов по шаблону АЦР. Архитектура отвечает на ограничения кейса: модели только из каталога Cloud.ru Evolution Foundation Models, развёртывание в выданной среде, единый API-эндпоинт для автопроверки, каркас ≤ 3 минут, комплект для 72 часов ≤ 20 минут, человек утверждает каркас до генерации содержания.

Главная идея: **LLM пишет тексты, а структура, арифметика и проверки — детерминированный код**. Модель предлагает формулировки и веса, солвер распределяет целые часы, валидаторы доказывают согласованность, а методист принимает решение на Human Gate.

| **Важно.** Жюри (О. Сычугов, GigaCowork) будет «очень глубоко» проверять каркас обучения. Поэтому архитектура строится вокруг каркаса: он хранится нормализованно, часы лежат только на уровне тем, итоги вычисляются, а утверждение с ошибками блокируется и в API, и триггером в БД (Д2 §6). |

# 4. Архитектурные принципы

**1. Детерминизм вокруг LLM.** Всё, что можно посчитать, считается кодом: выбор шаблона по правилам, часы, календарь, проверки, рендер. LLM отвечает строго по JSON-схеме (structured output), ответ валидируется Pydantic, при ошибке — до 2 попыток «ремонта» с текстом ошибки.

**2. Human-in-the-Loop как инвариант системы.** Статус framework_approved нельзя получить без утверждающего и без сходящихся часов (триггер program_gate); генерация комплекта до утверждения возвращает 409 GATE_NOT_PASSED. Это и «защита от холостого инференса» из аналитического отчёта.

**3. Единый источник истины.** Каноническая модель — нормализованные таблицы каркаса и содержания; KitV1 JSON — их сериализация; .docx/.pptx/GIFT — проекции KitV1. Повтор материала между файлами невозможен, потому что файлы не редактируются отдельно.

**4. Стабильные идентификаторы.** Каждый элемент имеет ref (C1, LO1.2, M2, T2.3, Q-017, ST-T2.3-1, LP-T2.3, SL-T2.3, SRC-04). На них строятся связи, точечные правки, отчёт и diff версий.

**5. Честность источников.** Код профстандарта, ТФ, номер приказа попадают в документ только из реестра; литература без подтверждения получает метку «не подтверждено» прямо в .docx.

**6. Лёгкость.** 4 типа процессов (Caddy, api, worker, PostgreSQL) + объектное хранилище. Никаких брокеров и отдельных векторных БД на этапе хакатона.

**7. Понятно методисту.** В интерфейсе нет слов «промпт», «токен», «LLM»; ошибки формулируются как в методической проверке: «Сумма тем модуля 2 — 20 ч, а модуль — 18 ч».

## 6.2. Параллелизм фазы 2

После утверждения каркаса содержание генерируется **параллельно по темам и модулям**: S11 строит рабочую программу модуля, затем для каждой темы независимо выполняются S12→S13, S14, S15. Граница параллелизма — семафор LLM-шлюза: не более 2 одновременных запросов на команду (лимит хаба); воркер запускается с `--concurrency 1`, чтобы два job не складывали свои семафоры. Связность обеспечивается тем, что каждый вызов получает «контекстный паспорт» темы: РО темы, соседние темы (для исключения повторов), глоссарий программы, уровень аудитории.

- **Только внутренние модели Cloud.ru.** В каталоге есть «внешние» модели (данные уходят за пределы Cloud.ru) и модели зарубежных разработчиков. Шлюз использует allowlist идентификаторов; модели зарубежных разработчиков не допускаются даже при доступности через каталог — чтобы не было спора с правилом кейса.

- **Structured output.** Ответы навыков — JSON по схеме (response_format/guided JSON, если поддерживается моделью; иначе — JSON-режим промпта + валидация). Невалидный ответ → «ремонт» с ошибкой валидации (≤ 2 раз) → смена на резервную модель → ошибка LLM_BAD_OUTPUT.

- **Температура.** Структура и проверки — 0,1–0,2; содержание — 0,4–0,6. Сид фиксируется, если модель его поддерживает.

- **Кэш.** Ключ = sha256(модель \| версия промпта \| сообщения \| параметры). Повторные автопрогоны одинаковых запросов не тратят токены; TTL 7 суток.

- **Учёт токенов.** Каждый вызов пишется в llm_call (навык, модель, токены, задержка, стоимость по тарифной таблице организации) — это данные для расчёта эффекта на защите.

- **Ретраи.** 429/5xx/таймаут → экспоненциальная задержка 1 → 2 → 4 с с джиттером; круговой предохранитель (circuit breaker) на модель: 10 ошибок за 60 с → пауза 5 с перед следующим обращением.

# 14. Надёжность и наблюдаемость

- **Идемпотентность:** Idempotency-Key для POST, создающих задачи; повтор автопрогона не порождает дубли.

- **Устойчивость задач:** зависшие задачи (locked_at старше 2 × таймаута) возвращаются в очередь; каждый навык сохраняет результат — перезапуск продолжается с последнего успешного шага.

- **Деградация:** при недоступности структурной модели каркас собирается резервной; при недоступности PyPI проверка версий выполняется по снимку каталога с пометкой в отчёте.

- **Метрики:** karkas_skill_seconds{skill}, karkas_llm_tokens_total{model,kind}, karkas_queue_depth, karkas_validation_errors_total{rule}, karkas_framework_seconds (SLO ≤ 180 с).

- **Логи:** JSON, корреляция по program_id, job_id, trace_id; тексты промптов в логи не пишутся, только хэш и размер.

- **SLO отборочного этапа:** доля успешных автопрогонов ≥ 99 %; p95 каркаса ≤ 90 с; p95 комплекта 72 ч ≤ 12 мин.
