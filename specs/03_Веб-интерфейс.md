# 1. Назначение и цели UX

Интерфейс КАРКАС — рабочее место методиста. Кейсодатель прямо предупреждает: «у методиста должен быть понятный, визуально удобный инструмент проверки… избегайте разработческого куража». Поэтому интерфейс строится вокруг **проверки и принятия решений**, а не вокруг чата с моделью.

| **Цель** | **Метрика** | **Как достигается** |
|:---|----|----|
| Методист собирает каркас без обучения | ≤ 3 действий от брифа до каркаса; без инструкции | Одна форма свободного текста + файлы; агент спрашивает недостающее |
| Ошибки каркаса видны сразу | Время обнаружения расхождения часов — 0 с | Живой пересчёт сумм в таблице, красная подсветка, подсказки «как исправить» |
| Связность видна глазами | Каждый РО — в матрице с темами и оценочными средствами | Вкладка «Связи» (матрица покрытия) |
| Правка без страха сломать | Перед правкой показан список затрагиваемых элементов | Предпросмотр влияния (dry_run) и diff версий |
| Понятный язык | 0 технических терминов ML на экранах | Словарь интерфейса (§12) |

# 2. Пользователи

# 4. Экраны

## 4.1. Новый запрос

<figure>
<img src="media/image2.png" style="width:6.49583in;height:4.06042in" />
<figcaption><p>Рисунок 3.2 — Экран «Новый запрос»: свободный текст, файлы и живое «что агент уже понял»</p></figcaption>
</figure>

- Поле брифа — многострочное, без ограничений формата; подсказка-пример из кейса («программа повышения квалификации на 72 часа…»).

- Зона загрузки принимает .docx, .pdf, .txt, .md до 50 МБ; для каждого файла агент предлагает роль (шаблон, образец структуры, профстандарт, старая программа), методист может изменить.

- Панель «Что агент уже понял» обновляется после разбора (S01, ≤ 10 с) — методист видит выбранный шаблон, объём, форму, аттестацию и нормативные замечания до сборки каркаса.

- Индикатор шагов (Запрос → Уточнения → Каркас → Утверждение → Комплект) показывает, где находится программа, и не даёт перескочить через Human Gate.

## 4.2. Уточнения

<figure>
<img src="media/image3.png" style="width:6.49583in;height:4.06042in" />
<figcaption><p>Рисунок 3.3 — Экран «Уточнения» на примере неполного запроса (тест-кейс 4)</p></figcaption>

- Не более 5 карточек; каждая объясняет, **зачем** спрашивается (одна строка мелким шрифтом).

- Варианты-кнопки + свободный ответ + «На ваше усмотрение» (агент берёт значение по умолчанию и записывает его в допущения отчёта).

- Карточка «Агент заметил» показывает разрыв между пожеланием и реалистичным результатом (ТК4-9).

## 4.3. Каркас · Учебный план (Human Gate)

<figure>
<img src="media/image4.png" style="width:6.49583in;height:4.06042in" />
<figcaption><p>Рисунок 3.4 — Учебный план с живой проверкой сумм и подсказками исправления</p></figcaption>
</figure>

- Редактируются только часы тем; строки модулей и итог — вычисляемые (как в БД).

- Нарушение подсвечивается на всех уровнях: ячейка → тема → модуль → итог; в правой панели — понятная причина и 2–3 кнопки исправления (вызов framework:rebalance с закреплёнными ячейками).

- Ячейки можно закрепить (замок) — солвер не меняет закреплённые значения.

- Кнопка «Утвердить каркас» неактивна, пока есть ошибки; рядом — объяснение, почему.

- Для форм с ДОТ появляется дополнительный столбец «из них дистанционно» (ТК2-2).

## 4.4. Каркас · Связи

<figure>
<img src="media/image5.png" style="width:6.49583in;height:4.06042in" />
<figcaption><p>Рисунок 3.5 — Матрица покрытия «результат обучения × темы × оценочные средства»</p></figcaption>
</figure>

- Строка — результат обучения с типом З/У/Н; столбцы — темы; последняя колонка — число оценочных средств с порогом ≥ 2.

- Клик по ячейке связывает/отвязывает РО и тему; клик по счётчику открывает список вопросов и заданий.

- Для разрыва агент предлагает конкретное исправление («Добавить вопрос к тесту модуля 5…»).

## 4.5. Комплект

<figure>
<img src="media/image6.png" style="width:6.49583in;height:4.06042in" />
<figcaption><p>Рисунок 3.6 — Комплект: дерево материалов, предпросмотр, точечная правка с планом влияния, самопроверка и выгрузка</p></figcaption>
</figure>

- Слева — дерево комплекта по разделам шаблона АЦР; бейджи показывают проблемы (например, «2 не подтверждены»).

- Центр — предпросмотр выбранного элемента (страница программы, слайды, вопросы с ключами, задание с критериями) и его связи (РО, вопросы, задания).

- Точечная правка: инструкция обычным языком → «Показать, что изменится» (dry_run) → «Применить». После применения — diff версии.

- Справа — итог самопроверки и блок «Эффект» (токены, стоимость по тарифу, оценка времени проверки).

# 8. Работа с данными

- **TanStack Query** — кэш серверного состояния; ключи \['program', id\], \['framework', id, version\], \['kit', id, version\]; ETag → 304.

- **SSE** (/programs/{id}/events): события progress, needs_input, framework_ready, kit_ready, edit_applied, job_failed; при обрыве — переподключение с Last-Event-ID.

- **Живой пересчёт часов на клиенте.** useLiveHours повторяет правила V-HRS-01…09 на TypeScript (общая спецификация правил в JSON), поэтому подсветка мгновенная; источником истины остаётся сервер (framework:validate с debounce 400 мс).

- **Оптимистичные правки** часов с откатом при ошибке; If-Match: lock_version защищает от одновременного редактирования.

- **Типы** генерируются из OpenAPI (openapi-typescript) — фронт и бэк используют одни имена полей KitV1.

# 11. Тестирование frontend

- Vitest + Testing Library: компоненты HoursGrid, CoverageMatrix, ImpactPreview; правила useLiveHours проверяются на тех же фикстурах, что и серверный солвер (общие JSON-кейсы).

- Playwright e2e: 5 открытых тест-кейсов как сценарии (бриф → вопросы → каркас → утверждение → комплект → выгрузка) на стенде с записанными ответами моделей.

- Визуальная регрессия ключевых экранов; axe-core на каждом экране.

- Юзабилити-проверка с 2–3 методистами на чекпоинте 1 (интерактивный прототип) — сценарий «найди и исправь ошибку в часах за 1 минуту».
